# Исследование

Этап `research`. Начинай его, когда бриф утверждён. Методика — [`research.md`](../knowledge/research.md). Сверка оснований — по [`evidence.md`](evidence.md), числа — по [`calculations.md`](calculations.md), бюджет — по разделу «Бюджет исследования» в [`run-case.md`](run-case.md). Формат записи `Q` — в [контракте](../contracts/README.md).

## План

1. Назови решение, которое должно последовать из работы.
2. Выпиши вопросы, от ответа на которые оно зависит. Оставь только те, что проходят проверку из методики: разные ответы ведут к разным действиям.
3. Запиши их в `research/questions.json`, статус `open`. В `affects` укажи, какой выбор зависит от ответа, в `needed_evidence` — что считать достаточным ответом.
4. Покажи план пользователю одним коротким списком и продолжай, подтверждения не жди. Если пользователь поправит план, поправь его, а работу не начинай заново.

## Работа

Иди от самого решающего вопроса. После каждого вопроса обнови запись: `status`, `findings`, `gap`.

| Что нашлось | Что записать |
|---|---|
| Основания достаточны | `answered`, `findings` с ID утверждений и расчётов, `gap: null` |
| Ответ неполный | `partial`, `findings` с тем, что есть, в `gap` — чего не хватает |
| Ответ недоступен: нет данных, доступа, бюджета | `blocked`, в `gap` — причина и что могло бы снять блокировку |
| Источники расходятся | утверждение со статусом `contested`, обе стороны сохранены по `evidence.md`, в `gap` записи `Q` названо расхождение |
| Показатель нельзя посчитать | расчёт `not_computable` по `calculations.md`, в `gap` — какие данные нужны |

Спорное утверждение не выбирай молча. Если одну сторону можно отвести, запиши причину по `evidence.md`. Если нельзя, вывод остаётся условным.

Новый вопрос по ходу работы добавляй, только если он проходит ту же проверку. Вопрос, потерявший значение, отзови с причиной.

## Остановка

Останавливайся, когда на каждый вопрос есть ответ, либо достигнут предел бюджета, доступа или времени. Не собирай сведения сверх решающих вопросов.

Когда бюджет исчерпан, действуй по `run-case.md`. Вопрос со статусом `open` на выходе из этапа не остаётся: он становится `blocked` с причиной.

Перед проверкой выхода пройди шаг 1 процедуры [`interviews.md`](interviews.md): есть ли вопросы `blocked` или `partial`, чей пробел касается мнений, поведения или готовности людей. Причины ухода клиентов, готовность платить, отношение к цене — такие пробелы. Если есть, задай пользователю вопрос о способе по шагу 2 и не уходи к вариантам, пока он не ответит. То же, если такой вопрос появился уже после проверки выхода, например его добавил пользователь: сначала вопрос о способе, потом всё остальное. Если вопрос о способе по этим пробелам уже задан и записан решением, второй раз его не задавай.

Скажи пользователю:

- чего хватает для условной рекомендации;
- чего не хватает и насколько это важно;
- что могло бы изменить решение.

## Выход

```text
.venv/Scripts/python.exe tools/gate.py check projects/<case-id> research
```

Вне Windows путь — `.venv/bin/python`. Если `passed` равно `false`, исправь названные записи и запусти проверку снова. Затем сохрани checkpoint с этапом `options`.
