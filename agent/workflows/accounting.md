# Учёт работы

Процедура общая для любой среды. Команды запускаются из корня папки: на Windows через `.venv/Scripts/python.exe`, в других системах через `.venv/bin/python`. Сеть не нужна.

Учёт показывает руководителю, сколько ушло времени и денег, где были ошибки и что он сделал сам. Цифры учёта выводит утилита из журнала действий и реестра вариантов: ты записываешь события, а не итоги. Команды журнала описаны в [процедуре сохранения](checkpoint.md#журнал-действий).

Главное правило: известное, оценка и неизвестное не смешиваются. Неизвестное не равно нулю, а подписка не делает работу бесплатной.

## Что записывать

- Каждый внешний или долгий шаг: чтение материала или сайта, поиск, расчёт, вызов модели с важным итогом, сохранение. Действие `start` пиши до шага, `end` после проверки результата. Ошибку записывай как `failed`, сомнение — как `unknown`, повтор — с `--retry-of` и причиной. По этим записям видны ошибки и повторы.
- В первом действии каждого чата передай ключи среды `--model`, `--runtime-version`, `--access`, `--cost-source`. Модель назови так, как её называет сама среда. Версию возьми из вывода команды версии самой среды, например `claude --version` или `codex --version`; нет такой команды — не передавай ключ. Тип доступа (`subscription`, `api`) и источник данных о расходе указывай, только если знаешь; не знаешь — не передавай ключ и не догадывайся. В отчёте это раздел «Среды и доступ», расход разбит по группам: модель, поиск и чтение сайтов, прочее. Если первым действием чата оказалось участие человека, передай ключи в следующем `action start`.
- Каждое участие человека — действием `human_input` (ниже).
- Время в журнал вручную не пиши: отметки ставит утилита. Отсчёт идёт с создания кейса.

## Участие человека

Запиши его сразу, как только ответ получен:

```text
tools/checkpoint.py action human projects/<case-id> --tool chat --environment claude_code --help-kind answer --note 'Уточнил, что сегмент — малый бизнес' --result-ref Q-0002
```

| `--help-kind` | Когда | Что ещё нужно |
|---|---|---|
| `choice` | Человек выбрал там, где нужен его выбор | `--result-ref DEC-…` и решение по [процедуре сохранения](checkpoint.md#журнал-действий) |
| `answer` | Ответил на уточнение по существу | ссылки на изменённые записи, если они есть |
| `material` | Передал файл или ссылку по ходу работы | ссылка `SRC-…`, если материал уже прочитан; иначе запиши без ссылки, не откладывая |
| `workaround` | Обошёл поломку руками: вошёл на сайт, перезапустил, скачал файл за агента | обязательно `--note`: что сделал |

- `--note` пиши своими словами, коротко, до 300 знаков. Слова пользователя для выбора хранятся в решении, а не здесь.
- Обход поломки отличай от участия по существу: «скачал отчёт, потому что сайт требует вход» — `workaround`, «дал отчёт о продажах» — `material`.
- `--active-minutes` — сколько времени, по словам человека, он потратил. Спроси об этом, когда участие заметное (поиск файла, обход поломки, долгий ответ). Не спрашивай после каждого короткого ответа. Не называет — не пиши: время останется неизвестным. Сам не оценивай: ты не видишь, сколько он думал, а сколько был занят другим. Итог за весь кейс спрашивай один раз, см. [ниже](#итог-кейса).

## Расход

Расход передаётся в `action end` файлом `--cost-file` с объектом `cost` из [контракта](../contracts/README.md). Без файла расход записан как неизвестный — это честное значение по умолчанию.

| Откуда число | Как записать |
|---|---|
| Среда показала расход: вывод `codex exec --json`, сообщение пользователя о показаниях `/cost` или страницы использования | Одно действие `model` с `--tool session`, `measured`. В `amounts` только то, что показано; остальное `null`. Все шаги после прежней такой записи, у которых нет своего расхода, считаются вошедшими в неё |
| Платный внешний API вернул число токенов или сумму | `measured` на действии, которое вызвало API |
| Ты оцениваешь по тарифу или длине текста | `estimated` с `estimate_source`: метод, а для денег — тариф и его дата вида `2026-11-06`. Без даты утилита и валидатор откажут |
| Ничего не известно | Не передавай файл |

Запрещено:

- писать токены, которых не видел;
- писать `money_usd: 0` по подписке Claude или ChatGPT;
- переводить долю подписки в деньги;
- записывать расход одного отрезка и на действии `session`, и на отдельных шагах: он посчитается дважды.

Участие человека в расход модели не входит: неизвестным итог делают только действия агента.

Пример оценки:

```json
{"basis": "estimated", "estimate_source": "тариф API на 2026-11-06, 3 $ за миллион входных токенов; токены по длине текста",
 "amounts": {"input_tokens": {"min": 40000, "max": 60000}, "output_tokens": null, "money_usd": {"min": 0.12, "max": 0.18}}}
```

## Итог кейса

Перед итоговой проверкой этапа `done`:

1. Спроси одной фразой, сколько времени у человека заняла работа над кейсом. Если назвал, запиши: `tools/checkpoint.py action human projects/<case-id> --tool chat --environment <среда> --help-kind answer --active-minutes <минуты> --covers-case`. Эта цифра заменяет названное раньше. Не назвал — не записывай.
2. Если среда показала расход или пользователь его сообщил, запиши его действием `session` (см. раздел о расходе). Нечего записать — итог останется неизвестным, это честный результат.
3. Построй отчёт: `tools/accounting.py report projects/<case-id>`.

## Сводка и отчёт

```text
tools/accounting.py summary projects/<case-id>
tools/accounting.py report projects/<case-id>
```

`summary` только читает. `report` пишет `outputs/accounting.md` и выводит ту же сводку. Отчёт не правь руками: его перепишет следующий вызов.

Строй отчёт перед сохранением на этапах `strategies`, `validation_plan` и `done`, а также когда пользователь спрашивает о времени или расходах. Тогда отчёт попадёт в checkpoint вместе с остальными текстами.

Что сказать пользователю:

- полное время и время до первых вариантов: это разные величины;
- сколько было ошибок и повторов и закрыты ли они;
- участие человека по видам и его время, если он его назвал;
- сколько источников использовано;
- расход тремя частями: что измерено, что оценено и по какому источнику, сколько действий без учёта. Если итог неизвестен, так и скажи: измеренное назови со словами «не меньше», оценку отдельно. Говори обычными словами, откуда число и чего в нём нет: «По показаниям среды ушло не меньше 37,4 млн входных и 242 тыс. выходных токенов: расход оборванного запуска сюда не вошёл. Сколько это в деньгах, неизвестно».

Отчёт отвечает за то, что записано. Шаги, которые ты не записал, в нём не видны: поэтому журнал ведётся с начала работы. Действие, оставшееся открытым на время перерыва, закрывай по проверенному результату: не удалось проверить — `unknown`; проверено — `completed` с ключом `--interrupted`. Так перерыв не войдёт во время в работе.

Отказы, код 4: `case_missing` — неверная папка; `journal_corrupt` — журнал повреждён не в последней строке, скажи пользователю; `unsafe_path` — на месте отчёта лежит не файл. `JOURNAL_TORN` в `warnings` — последняя строка журнала оборвана и пропущена. `FIRST_RESULT_BEFORE_JOURNAL` — варианты датированы раньше начала отсчёта, время до первого результата занижено: назови это. `FIRST_RESULT_UNSTAMPED` — завершённое действие не называет самый ранний вариант в `--result-ref`, время до первых вариантов взято из записи агента: назови это. `LONG_ACTION_COUNTED` — во время в работе вошло действие дольше 30 минут без промежуточных записей: если на него пришёлся перерыв, скажи, что время завышено. Код 5 — сбой утилиты, повтори вызов.

Отказы `action human`: `human_result_invalid` — для выбора нужен `DEC`; `human_note_missing` — для обхода поломки нужна заметка; `human_time_invalid` — время должно быть неотрицательным числом; `human_total_invalid` — итог за кейс без времени; `ref_unknown` — запись, на которую ссылаешься, ещё не создана.
