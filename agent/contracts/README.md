# Контракты данных кейса

Этот каталог описывает формат папки кейса `projects/<case-id>/`. По нему исполнитель, не читавший спецификацию, пишет запись любой сущности, а валидатор `tools/validate_project.py` проверяет форму и связи. Источник правил — [спецификация B01](../../docs/specs/2026-11-05-b01-contracts.md); при расхождении верна она.

Состав каталога:

- `versions.json` — поддерживаемые версии формата и миграции;
- `schemas/*.schema.json` — JSON Schema (Draft 2020-12), по одной на тип файла, общие определения в `common.schema.json`;
- `examples/valid/demo-case/` — связный кейс с вымышленными учебными данными, образец для всех типов записей;
- `examples/invalid/<случай>/` — по одному нарушению на папку, только для тестов;
- [`modes.md`](modes.md) — правила режимов продукта и разработки;
- `records/*.md` — формат каждого вида записи, по файлу на вид;
- [`error-codes.md`](error-codes.md) — коды ошибок валидатора.

Пользовательские кейсы лежат в `projects/`, этот каталог в `.gitignore` и не публикуется. Кейс не должен зависеть от чата, `.work/`, личных путей и секретов.

## Папка кейса

| Путь от корня кейса | Содержимое | Запись |
|---|---|---|
| `case.json` | версия формата, `case_id`, название, дата создания, необязательный `options_format` | один раз; единственный обязательный файл |
| `brief.md` | бриф | текст, без контракта; утилиты читают разделы `Бюджет исследования` и `Слова пользователя` |
| `sources/` | копии материалов (беседы с модельными клиентами — `sources/interviews/synthetic-<персонаж>-<n>.md`, разделы `## Вопрос N`; шапка: персонаж, дата, среда, изоляция; при включённом маршруте ещё `Модель:` и `Проверка роли:`, см. | `evidence/calculations.json` | расчёты (`CALC`) | реестр |

| `outputs/interview-guide.md` | гайд бесед с модельными клиентами | текст со ссылками; пишется на этапе `research`, если выбран `interview_method` |
| `research/interviews/personas.md` | карточки персонажей для бесед | текст; изменение карточки — новая беседа; закрепляется в checkpoint и возвращается вместе с ним |

| `outputs/case-page.html` | страница кейса: решение, команда и сроки, варианты, основания, пересмотры, учёт | собирается `tools/case_view.py build projects/<case-id>` на любом этапе; в checkpoint не входит, при каждой сборке пишется заново |
| `outputs/revisions.md` | журнал пересмотров после новых данных | только дописывание в конец; формат ниже |
| `outputs/.history/<N>/` | копии файлов `outputs/*.md` до пересмотра номер `N`, кроме `revisions.md` | пишет `tools/revision.py snapshot`; после записи не меняются; валидатор папку пропускает |
| `state/actions.jsonl` | журнал действий (`ACT`) | только дописывание |
| `state/checkpoints/CKP-NNNN.json` | checkpoint (`CKP`) | новый файл на каждое сохранение |
| `state/snapshots/<sha256>` | копии артефактов checkpoint, имя — отпечаток содержимого | файлы не меняются и не удаляются; пишет `tools/checkpoint.py` |
| `state/interviews/rejected-<персонаж>-<n>.md` | беседа, отклонённая проверкой роли и замещённая повтором ([маршрут](../workflows/interview-routing.md)) | новый файл на каждый провал; в источники не попадает; текст без контракта, валидатор и проверка этапа его не читают |
| `state/reviews/review-NNNN.md` | независимые проверки документов: ответ проверяющего и разбор замечаний ([процедура](../workflows/strategies.md#независимая-проверка)) | новый файл на каждую проверку; текст без контракта, валидатор и проверка этапа его не читают |

Реестр — JSON-объект `{"format_version": 1, "records": [...]}` (у `case.json` есть необязательный признак `options_format`, см. «Версии формата»). Нет файла реестра — реестр пуст. Записи не удаляются: отзыв выражается статусом и причиной.

## ID, даты, пути

- ID имеет вид `ПРЕФИКС-NNNN`, минимум четыре цифры: `SRC`, `CLM`, `CALC`, `Q`, `OPT`, `DEC`, `ACT`, `CKP`. Следующий номер — максимальный существующий плюс один, дополненный нулями.
- ID уникален в кейсе и не используется повторно, в том числе после отзыва. Префикс задаёт тип: ссылка на запись другого типа — ошибка `ID_WRONG_TYPE`.
- `case_id`: строчные латинские буквы, цифры и дефис; совпадает с именем папки кейса.
- Даты — RFC 3339 со смещением: `2026-11-05T14:30:00+03:00` или с `Z`. Несуществующая дата, дата без смещения или с пробелом вместо `T` — `SCHEMA`.
- Значения ID, `topic` и `case_id` проверяются целиком: перевод строки в конце, не-ASCII цифры и лишние символы — `SCHEMA`.
- Пути в записях — относительные от корня кейса, через `/`. Нельзя: начало с `/`, обратная косая черта, двоеточие (буква диска), сегменты `.` и `..`, выход за корень. Нарушение — `PATH_UNSAFE`. Путь файла источника начинается с `sources/`. `url` источника и `source_url` — только `http` или `https`, иначе `PATH_UNSAFE`; абсолютный путь в `reproduce` расчёта — тоже.
- Неизвестное значение записывается как `null`, а не нулём и не пустой строкой. Необязательные поля (`status_reason`, `source_url`, `supersedes`, `change_reason`, `choice`, `retry_of`, `retry_reason`, `runtime`, `delegated`, `resolution`, `quote`, `estimate_source`, `amounts`) при отсутствии значения не пишутся вовсе, `null` в них не допускается. `null` допустим только там, где он назван в описании типа (например, `proposal`, `limits`, `gap`, `model`, `previous`, `sha256` для `url`).

## Изображения и наблюдения

Расширение перечислений `type` и `locator.kind` не меняет версию формата: кейсы без изображений читаются без изменений.

- **Регистрация.** `tools/read_material.py add` принимает `.png`, `.jpg`, `.jpeg`, `.webp`. Формат проверяется по заголовку, а не по расширению; читаются формат, ширина и высота, пиксели и содержимое не читаются. Подделанное расширение, обрезанный файл (у PNG в последних 64 байтах нет блока `IEND`, у JPEG нет маркера конца `FF D9`) и анимация (WebP с флагом анимации, PNG с блоком `acTL`; причина «анимация не поддерживается») — код 2, источник не записывается. Сторона больше `max_image_side` — как у других форматов: источник записывается со статусом чтения `over_limit`, код 3, наблюдения для него не принимаются. После успешного `add` источник `partial`, `complete: false`, блоков нет, в `limits` «Изображение PNG 1366×768. Наблюдения не записаны.»; файл `sources/extracted/<SRC-id>.jsonl` пустой, `EXTRACT_MISSING` не выдаётся. Очень высокое изображение (высота больше ширины в 2,5 раза) получает в `limits` пометку, что детали могут потеряться.
- **Наблюдения.** Агент смотрит изображение и пишет файл `sources/incoming/<имя>.md`, `tools/read_material.py add-observations <case> <SRC-id> --text-file <файл>` разбирает его и пишет блоки `region`. Формат файла: `## Экран` (метка `целевой`, `заслонён`, `вход`, `капча`, `ошибка`, `пусто` или `другое` и одна строка), `## Наблюдение N` с N с единицы подряд (три строки `Где:`, `Видно:`, `Текст:`; строка `Текст:` — либо ровно `нет`, либо ровно `неразборчиво`, либо только цитаты в «…», разделённые запятыми, точками с запятой или пробелами; всё вне кавычек — ошибка формата), `## Не разобрано` (обязателен, допустим `нет`). Блок: `{"n": N, "locator": {"kind": "region", "index": N, "area": "<строка Где>"}, "text": "Где: …
Видно: …
Текст: …"}`. `quote` проверяется только по части блока после `Текст:`: место (`Где:`), описание (`Видно:`) и сами метки не цитируются.
- **Статусы.** Метка не `целевой`: `unavailable`, блоков нет (выход 2). Метка `целевой`: нужно хотя бы одно наблюдение, статус `ok`, если `## Не разобрано` — `нет` и снято всё, иначе `partial`. Повторная команда переписывает наблюдения, пока на источник нет ссылок; после ссылки — отказ (код 4), источник отзывают и регистрируют заново.
- **Снимки страниц.** `tools/read_material.py capture-web <case> --url <адрес> --title <название> [--mobile]` (необязательная группа `screenshots`) записывает части страницы как источники `image` с `origin: public_web`, `location.path` вида `sources/capture-<SRC-id>.png`, общими `source_url` (адрес после переадресации) и `retrieved_at` и названием «<название>, экран i из n». Все части попадают в реестр одной записью. Если снята не вся страница, у последней части в `sources/extracted/<SRC-id>.report.json` стоит `capture_incomplete` («Снято k из n экранов.»), статус остаётся `partial`, а `add-observations` сохраняет эту пометку в начале `limits` и не поднимает статус до `ok`. Адрес и каждый шаг цепочки переадресаций проверяются правилом публичных адресов, запросы страницы пропускаются только к публичным адресам, всплывающие окна закрываются, сокеты не соединяются. Правило применяется к имени, которое видит программа, а браузер разрешает его сам ещё раз, поэтому защита от подмены ответа DNS между двумя разрешениями не гарантируется (ограничение записано в [environments.md](../../docs/environments.md#изображения-e04)). Весь снимок ограничен `capture_timeout_seconds` плюс запас: по истечении браузер останавливается, ответ — `timeout`.
- **Признаки отказов.** `capture_unavailable` (нет Playwright или браузера, в ответе поле `install` с двумя командами), `budget_exhausted`, `action_missing` и `fetch_error`: `network_unavailable`, `address_blocked`, `http_error`, `timeout`, `blank_page`, `capture_unreadable`.
- **Утверждения.** `region` допустим только для `image` (иначе `LOCATOR_MISMATCH`), несуществующий номер наблюдения — `LOCATOR_NOT_FOUND`, цитата не из наблюдения — `QUOTE_NOT_FOUND`. Правила, что из наблюдений факт, а что гипотеза, — [методика](../knowledge/ux-review.md).

## Версии формата

`format_version` — целое число, сейчас `1`. Оно есть в `case.json`, каждом реестре, каждом checkpoint и каждой строке журнала; у Markdown версии нет. Поддерживаемые версии перечислены в `versions.json`:

```json
{"current": 1, "supported": [1], "migrations": {}}
```

- Неизвестная версия в `case.json`, реестре или строке журнала: `FORMAT_UNSUPPORTED`, валидатор останавливается и записи не читает.
- Checkpoint с неизвестной или отличной от `case.json` версией проверку не останавливает и ошибок `FORMAT_*` не даёт: он негоден, текущим становится более ранний (`CHECKPOINT_FALLBACK`).
- Известная версия, отличная от версии `case.json`: `FORMAT_MIXED`.
- Признак `options_format`: в `case.json` необязательное свойство `"options_format": 2` (допустимо только значение `2`, иное — `SCHEMA`). Это переключатель кейса для полей `cost` и `limit_check` варианта и проверок `gate` из раздела «Проверка этапа»: с признаком поля допустимы и проверяются, проверки действуют; без него поля не допускаются (`SCHEMA`), проверки не применяются, и кейс проверяется как до их появления. Версия самого реестра вариантов остаётся `1`, как у всех реестров: утилиты чтения реестров принимают только её, а реестр версии 2 — `FORMAT_UNSUPPORTED`. `tools/case.py new` пишет признак в `case.json` и реестр вариантов не создаёт; образец `valid/demo-case` и все ранее созданные кейсы признака не имеют.
- Нет поля или оно не целое (`1.0`, `true`, строка): `SCHEMA`.

Миграция. Несовместимое изменение формата увеличивает версию. Вместе с новой версией добавляется `tools/migrate_v<N>.py`: он создаёт рядом копию кейса в новом формате, исходная папка не меняется, результат проходит валидатор. В `versions.json` в `migrations` записывается ключ `"<N>"` со ссылкой на скрипт, версия добавляется в `supported`. Изменение контракта согласуется с владельцами зависимых задач в PR. Пока версия одна, скрипта нет.

## Статусы и отзыв

| Тип | Как отзывается | Причина |
|---|---|---|
| `SRC`, `CALC`, `Q`, `OPT` | `record_status`: `active` или `withdrawn` (`SRC` — `tools/evidence.py withdraw`) | при `withdrawn` обязателен `status_reason` |
| `CLM` | `status: withdrawn` (`tools/evidence.py withdraw`) | обязателен `status_reason` |
| `DEC` | `status: superseded` | причина в `change_reason` заменяющего решения |
| `ACT`, `CKP` | не отзываются | — |

Правила связей проверяют только активные записи: отозванные и замещённые остаются в истории и не блокируют кейс. Активная запись не может ссылаться на отозванную (`WITHDRAWN_USED`). Это относится к вариантам, решениям, вопросам, расчётам и ссылкам `[ID]` в `outputs/**/*.md`.

## Записи по типам

Все поля, кроме помеченных необязательными, обязательны. Лишних полей быть не может. У каждой записи реестра есть `id` и `created_at`. Время в реестрах берётся из системных часов в момент записи: команда `date +%Y-%m-%dT%H:%M:%S%:z`.

Формат каждого вида записи описан в отдельном файле. Агент читает этот файл сразу, а файл вида записи — перед тем, как писать запись этого вида.

| Вид записи | Файл |
|---|---|
| Источник `SRC`, извлечённый текст, локатор | [`records/source.md`](records/source.md) |
| Утверждение `CLM` | [`records/claim.md`](records/claim.md) |
| Расчёт `CALC` | [`records/calculation.md`](records/calculation.md) |
| Вопрос исследования `Q` | [`records/question.md`](records/question.md) |
| Вариант `OPT` | [`records/option.md`](records/option.md) |
| Решение `DEC` | [`records/decision.md`](records/decision.md) |
| Действие `ACT` | [`records/action.md`](records/action.md) |
| Checkpoint `CKP` | [`records/checkpoint.md`](records/checkpoint.md) |
| Тексты `outputs/**/*.md` | [`records/outputs.md`](records/outputs.md) |
| Журнал пересмотров `outputs/revisions.md` | [`records/revisions.md`](records/revisions.md) |
| Коды ошибок валидатора | [`error-codes.md`](error-codes.md) |

## Проверка этапа

```text
.venv/Scripts/python.exe tools/gate.py check projects/<case-id> <этап> [--preliminary]
```

Этапы: `research`, `options`, `decision`, `strategies`, `validation_plan`, `done`. Проверка накопительная и ничего не пишет. Первая строка вывода — JSON с `passed`, `problems` и `warnings`, элементы содержат код, файл, ID и пояснение без текста материалов. Коды выхода: 0 пройдено, 1 найдены проблемы, 4 отказ, 5 сбой. Ошибки валидатора прекращают проверку: сначала идёт общая проблема `CASE_INVALID` со списком кодов, затем каждая ошибка валидатора отдельной проблемой со своим кодом, файлом и пояснением. Если ошибок так много, что вывод вышел бы за предел `max_output_chars`, последней идёт проблема `VALIDATOR_ERRORS_NOT_SHOWN` с числом непоказанных ошибок: полный список даёт `tools/validate_project.py`. `--preliminary` допустим для `strategies` и `validation_plan`.

| Код | Условие |
|---|---|
| `RESEARCH_EMPTY`, `RESEARCH_OPEN`, `RESEARCH_NO_FINDING`, `RESEARCH_NO_GAP`, `RESEARCH_HIDDEN_CONFLICT` | нет вопросов, вопрос открыт, ответ без оснований, пробел не назван, спорное основание без пробела |
| `OPTIONS_TOO_FEW`, `OPTIONS_NO_KEEP`, `OPTIONS_NO_CLOSE`, `OPTIONS_NO_DEVELOP`, `OPTIONS_DUPLICATE`, `OPTION_FIELD_EMPTY`, `OPTIONS_TABLE` | требования к набору и полям вариантов, вариант не в таблице сравнения |
| `OPTION_COST_MISSING`, `OPTION_COST_UNFOUNDED`, `OPTION_COST_GAP`, `OPTION_GAP_NOT_SHOWN`, `OPTION_LIMIT_MISSING`, `OPTION_LIMIT_STALE`, `OPTION_LIMIT_UNFOUNDED` | только при `options_format: 2` в `case.json`, у каждого действующего варианта, на этапе `options` и на всех следующих. Нет `cost`; `estimated` без расчётов, расчёт не `computed` или отозван либо его нет в `basis`; `not_estimated` с вопросом не в статусе `partial` или `blocked` либо без `gap`; вопрос из `cost.question_id` не назван ссылкой `[Q-…]` в разделе `Чего не хватает` файла `outputs/options.md`; нет `limit_check`; `limit_check.brief_decision` не совпадает с действующим решением `brief` в статусе `chosen` (`null`, если такого нет): после нового решения `brief` проверка не проходит ни на одном этапе, пока сверки не пересчитаны; `fits` или `exceeds` без посчитанного расчёта в `basis` (`fits` без `calc_id` допустим при `cost.status: none`), `exceeds` при `cost.status: none` либо любой из двух при `cost.status: not_estimated`. Сообщение называет поле и что в нём должно быть |
| `OPTIONS_COST_UNKNOWN`, `CHOICE_EXCEEDS_LIMIT` | предупреждения при `options_format: 2`: ни у одного варианта `develop` нет `cost.status: estimated`; предложенный или выбранный вариант направления имеет `limit_check.result: exceeds` (человек вправе выбрать его, если ему об этом сказано) |
| `THRESHOLD_BASIS_MISSING` | только при `options_format: 2` в `case.json`, на `validation_plan` и `done`: в разделе `Условие успеха и неуспеха` файла `outputs/validation-plan.md` нет ни одной ссылки на расчёт `[CALC-…]` или вопрос `[Q-…]`. Проверка грубая: одна ссылка на раздел, а не на каждый порог |
| `PROPOSAL_MISSING`, `DECISION_PENDING` | нет решения `direction`, нет выбора человека |
| `OUTPUT_MISSING`, `OUTPUT_SECTION`, `STATUS_LINE`, `WRONG_OPTION`, `SECTION_UNLINKED`, `PRELIMINARY_LEFT` | структура файла, статус, связь с выбором, раздел с выводом без ссылки, предварительный статус на `done` |
| `PROMISE_TABLE`, `PROMISE_WEAK`, предупреждение `PROMISE_PLANNED` | таблица обещаний, основание неподтверждённое, основание только выбранный вариант |
| `NUMBER_UNLINKED`, `NUMBER_MISMATCH`, `NUMBER_AMBIGUOUS` | число без ссылки, не совпадает с записью или брифом, знак не читается |
| `INTERVIEW_METHOD_MISSING` | есть активный синтетический источник или `outputs/interview-guide.md`, а действующего решения `interview_method` в статусе `chosen` нет; либо источник создан раньше первого выбора способа. Повторный выбор (новое решение `interview_method` через `supersedes`) не отменяет прежние беседы: срок отсчитывается от самого раннего решения по цепочке `supersedes` |
| `INTERVIEW_GUIDE` | `outputs/interview-guide.md`: нет статус-строки `Статус: способ выбран [DEC-…]` либо она не ссылается на действующее решение `interview_method`; нет ни одного раздела `Q-NNNN. …`; раздел `Q-NNNN. …` неверного вида, с несуществующим `Q` или с `Q` не в статусе `partial` или `blocked`. Разделы `Кого спрашивать` и `Согласие и данные` и числа проверяются кодами `OUTPUT_SECTION` и `NUMBER_*` |
| `INTERVIEW_LIMIT` | больше трёх активных синтетических источников без решения `budget` в статусе `chosen`, принятого после первого выбора способа (самого раннего решения `interview_method` по цепочке `supersedes`, повторный выбор срок не сдвигает); считаются только активные источники, заменённая повтором беседа отозвана и не в счёт; либо больше десяти разделов `## Вопрос N` в одной беседе |
| `SYNTHETIC_UNMARKED` | в `outputs/options.md`, `product-strategy.md`, `communication-strategy.md`, `validation-plan.md` или `commitments.md` ссылка на утверждение или расчёт с синтетическим основанием (в `supports` синтетический источник, в том числе отозванный, транзитивно через `derived_from` и входы расчёта) без пометки `(синтетика)` сразу после ссылки; ссылки на варианты пометки не требуют |
| `THRESHOLDS_PENDING`, `THRESHOLDS_NOT_CITED`, `ACTIONS_OPEN` | пороги не согласованы либо согласованы раньше текущего выбора, `outputs/validation-plan.md` не ссылается на действующее решение `thresholds`, действие начато и не закрыто |
| `COMMITMENTS_PENDING` | на `done`: нет действующего решения `commitments` с выбором человека, либо оно принято раньше текущего выбора направления |
| `COMMITMENTS_NOT_CITED` | раздел `Согласование` в `outputs/commitments.md` не ссылается на действующее решение `commitments` |
| `COMMITMENTS_TABLE` | таблица `Действия`: другие колонки, нет строк, в строке пустая ячейка или нет ссылки в `Основание` |
| `TEAM_FORMAT` | на `validation_plan` и `done`: `team.md` есть, но нет строки `Источник` с существующим завершённым действием `human_input`, либо нет ни таблицы с колонками `Имя`, `Роль`, ни строки «Состав не назван», либо имя повторяется, содержит запятую или ячейка пуста |
| `TEAM_UNKNOWN_OWNER` | в `team.md` есть таблица, а в колонке `Ответственный` строки `Действия` стоит имя не из неё; имена через запятую, сравнение точное после сжатия пробелов |
| `TEAM_NOT_ASKED` | предупреждение: `outputs/commitments.md` есть, а `team.md` нет |
| `REVIEW_UNLINKED` | условие пересмотра в `outputs/commitments.md` без ссылки |
| `REVISION_FORMAT` | `outputs/revisions.md`: нет заголовка `# Пересмотры`, неверный заголовок записи, не хватает или повторяется строка записи, `Выбор` или `Прежние версии` не в допустимой форме |
| `REVISION_NUMBER` | номера записей идут не подряд с 1 |
| `REVISION_UNRECORDED` | есть решение `revision`, а журнала нет, либо решение названо не ровно в одной записи |
| `REVISION_NO_SNAPSHOT` | у записи с решением нет непустой папки `outputs/.history/<N>/` |
| `REAPPROVAL_PENDING` | пересмотр затронул `validation-plan.md` или `commitments.md`, а действующее решение `thresholds` или `commitments` принято раньше этого пересмотра |

## Валидатор

```text
.venv/Scripts/python.exe tools/validate_project.py <папка кейса> [--json]
```

Код выхода: `0` — ошибок нет, `1` — есть ошибки, `2` — неверный вызов, `3` — внутренний сбой валидатора: текст исключения не печатается (там могут оказаться данные кейса), а с `--json` выводится объект с `"internal_error": true`. Вывод содержит код, файл, ID записи и короткое пояснение, без содержимого полей и материалов. `--json` печатает `{"errors": [...], "warnings": [...], "current_checkpoint": "CKP-0002"}`; элемент списка — `{"code", "file", "record_id", "message"}`, `current_checkpoint` — ID текущего checkpoint или `null`. Файл checkpoint — `state/checkpoints/<ID>.json`. Валидатор только читает.

Коды ошибок валидатора — в [`error-codes.md`](error-codes.md).

## Примеры

`examples/valid/demo-case/` — полный завершённый кейс: по записи каждого типа, отозванное утверждение, снятое противоречие, замещённое решение, действие с неизвестным расходом, два checkpoint, документы всех этапов с согласованными порогами и обязательствами, отчёт учёта и один записанный пересмотр со снимком в `outputs/.history/1/`. `tools/gate.py check` проходит на нём этап `done`. `examples/valid-cost/` — наложение на него: `case.json` с `options_format: 2`, реестр вариантов с `cost` и `limit_check` у каждого варианта, раздел порогов плана со ссылками на расчёты и обновлённый хэш плана в checkpoint (собирается так же, как случаи `invalid/`); `gate` проходит на нём `done`. Файл `examples/valid/expected-warnings.json` перечисляет предупреждения образца тройками `code`, `file`, `id` (сейчас одно стоячее `BASIS_UNCONFIRMED` на ссылку в `outputs/commitments.md` на гипотезу из синтетической беседы).

`examples/invalid/<случай>/` содержит нарушение одного правила как наложение на `valid/demo-case/`:

- `expected.json` — `{"errors": ["КОД"], "warnings": []}`: точный набор ожидаемых кодов; необязательное `"delete": ["путь/от/корня/кейса"]` — файлы образца, которые убираются; необязательное `"supported_versions": [1, 2]` — версии, считающиеся поддерживаемыми в этом тесте;
- остальные файлы папки повторяют путь от корня кейса и заменяют файлы образца целиком.

Недействительные образцы `option-cost-type` (`cost` без `calc_ids`), `option-cost-link` (расчёт, которого нет), `option-cost-no-marker` (поля `cost` и `limit_check` без `options_format` в `case.json`) и `option-marker-invalid` (`options_format: 3`) проверяют типы, ссылки и признак; в двух первых `case.json` содержит признак; новых кодов валидатора они не вводят, а проверки `gate` покрыты тестами `tests/test_option_cost.py`.

Тест собирает образец и наложение во временную папку `demo-case` (имя должно совпадать с `case_id`) и запускает валидатор. Хэши файлов в примерах зависят от байтов, поэтому для `agent/contracts/examples/` в `.gitattributes` отключены преобразования строк.
