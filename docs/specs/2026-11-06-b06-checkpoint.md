# B06. Сохранение и продолжение

Спецификация карточки [B06](../tasks/CORE.md). Статус: согласована.

## Зачем

Руководитель продукта останавливает работу и возвращается в новом чате, возможно в другой среде. Вся память о кейсе должна лежать в его папке. Контракт B01 описал формат checkpoint и журнала, валидатор их проверяет, но ни один инструмент их не пишет. Без этого агент составлял бы JSON руками и мог бы записать то, чего не было: завершённое действие, выбор человека, этап `done`.

Нужно закрепить за инструментом запись и восстановление, а агенту оставить смысловую часть: цель, этап, открытые вопросы и следующий шаг.

## Цели и отказы

Цели:

- журнал действий дописывается инструментом, с отсечением оборванной строки и отказом на незаметный повтор;
- checkpoint публикуется только после проверки кейса и сохранения копий файлов, прерывание на любом шаге не даёт ложного «всё завершено»;
- факты в checkpoint выводятся из журнала и реестров, а не со слов агента;
- новый чат получает из одной команды цель, этап, сделанное, выбор человека, открытое, следующий шаг и отличия от сохранённого;
- повреждённый реестр или текст возвращается из копии; потеря видна и признаётся явно;
- одна процедура для Claude Code и Codex, перенос папки не требует ничего, кроме неё самой.

Не входит: фоновый мониторинг и автоматический пересмотр стратегии (E01); полный учёт времени, расхода и сводка (B13); `START.md`, этапы и команды естественным языком (B07); живые прогоны в новом чате и перенос между средами (B09, B12); одновременная работа двух чатов над одним кейсом; миграция форматов.

Провалом считается инструмент, после прерывания которого новый чат не отличает сделанное от начатого, либо молча повторяет действие, либо считает выбором человека то, чего человек не выбирал.

## Инструмент

`tools/checkpoint.py <команда> <папка кейса> …`. Команды запускаются из корня репозитория интерпретатором `.venv`, как `tools/read_material.py`. Первая строка вывода — JSON-отчёт. Коды выхода: `0` — успех, `1` — отказ по существу (причина в `refused`), `2` — неверный вызов, `3` — внутренний сбой без текста исключения. Отказ ничего не меняет в кейсе.

Свои проверки инструмент делает через `validate_case` из `tools/validate_project.py`, правила годности checkpoint не дублирует. Для этого `Report` дополняется списком `checkpoints`: у каждого файла `name`, `number`, `seq`, `reason` (`null` у годного) и `previous` и `missing` (все отсутствующие артефакты; раньше проверка останавливалась на первом). Список заполняется и тогда, когда валидатор останавливается из-за неподдерживаемой версии файла: так `restore` работает и в этом случае. Формат вывода и коды не меняются, уточняются правила:

- потерянным считается негодный файл с номером больше номера `previous` текущего checkpoint (0, если `previous` — `null`), а также посторонний файл; негодный файл с меньшим номером не потерян;
- если файл `previous` существует, но не читается, `seq` с ним не сравнивается: цепочка не рвётся из-за повреждения предшественника;
- скрытые `.lost-CKP-NNNN.json` и `.rejected-CKP-NNNN.json` занимают свой ID: ссылка на него из журнала не даёт `ID_MISSING`, запись считается недоступной, как у повреждённого checkpoint;
- файлы `outputs/`, чьё имя или имя папки начинается с точки, текстами не считаются.

Каталог `state/snapshots/` валидатор не читает.

### `action`: журнал

- `action start <case> --kind … --tool … --environment … [--model …] [--input-ref ID]… [--retry-of ACT-… --retry-reason …]` выдаёт новый `ACT-NNNN` и пишет строку `start`.
- `action end <case> --id ACT-… --outcome completed|failed|unknown [--result-ref ID]… [--cost-file путь]` пишет строку `end`. Без `--cost-file` расход `{"basis": "unknown"}`. Формат файла — объект `cost` из контракта.
- `action human <case> --tool … --environment … --result-ref DEC-…` пишет обе строки сразу, как требует контракт для `human_input`.

Запись: под уникальный ID берётся максимальный номер плюс один, в том числе из оборванной строки, если он читается. Перед дописыванием отсекается неразбираемый хвост: последняя строка, которая не читается как JSON, с переводом строки или без (так же её видит валидатор, `JOURNAL_TORN`). Читаемая последняя строка без перевода строки сохраняется, к ней добавляется перевод строки. Затем строка дописывается с `fsync`. Строка проверяется схемой до записи.

Ссылки `--input-ref`, `--result-ref` и `--retry-of` должны называть существующую запись: ID из реестров, журнала или файла checkpoint (скрытые файлы тоже считаются). ID реестра, который не читается, не проверяется. Исключение — решения `DEC-…` в `action human`: запись о выборе создаётся после действия.

Отказы `action start`:

- строка журнала не в конце не разбирается (`FILE_CORRUPT`): дописывать нельзя;
- без `--retry-of` в журнале есть действие с теми же `kind`, `tool` и тем же непустым множеством `input_refs`, с любым исходом, в том числе `failed` или ещё не записанным. Ответ называет это действие. Так причина любого повтора остаётся в журнале. Если такое действие найдено, `--retry-of` должен указывать на действие с теми же `kind`, `tool` и `input_refs`, иначе отказ (`retry_target_mismatch`).

Действия с пустыми `input_refs`, например вызов модели без ссылок, инструмент не сравнивает: одинаковые аргументы там не означают одно действие. Для них защитой служит сводка `resume`.

Строка `end` для действия с уже записанным концом — отказ. Начатое без конца закрывается обычным `action end` после проверки результата. Записанный `outcome: unknown` остаётся в журнале навсегда, потому что второго конца быть не может: и проверка, и настоящий повтор идут новым действием с `--retry-of` на него и причиной.

Действие без конца или с исходом `unknown` считается снятым, если выполненное (`completed`) действие повторяет его через `--retry-of`, в том числе по цепочке повторов. Снятое действие не блокирует `done` и не входит в `actions_unknown`; `resume` показывает его в `actions_resolved` с полем `resolved_by`. Повтор с исходом `failed` или `unknown` ничего не снимает.

### `save`: новый checkpoint

`save <case> --from <файл JSON> [--acknowledge-loss]`. Файл содержит `goal`, `stage`, `open_items`, `next_step`; `goal` можно опустить, тогда он берётся из текущего checkpoint. Текст не передаётся аргументами: содержимое кейса в командной строке интерпретируется оболочкой.

Шаги строго по порядку:

1. Прогнать валидатор. Любая ошибка — отказ с перечнем кодов. Если текущий checkpoint негоден и есть потери (`CHECKPOINT_FALLBACK` или `CHECKPOINT_NONE_VALID`), без `--acknowledge-loss` отказ. С флагом `CHECKPOINT_NONE_VALID` не считается ошибкой, новая цепочка начинается с `previous: null`, `seq: 1`, и признанные потери убираются на шаге 7.
2. `stage: done` при действиях без исхода или с исходом `unknown` — отказ, кроме действий, снятых повтором.
3. Собрать артефакты автоматически, только существующие файлы: `brief.md`, реестры `REGISTRIES`, карточки персонажей `research/interviews/personas.md` (добавлены с E03), все `outputs/**/*.md`; файлы и папки с точкой в начале имени пропускаются. Артефакт или папка снимков, оказавшиеся вне папки кейса, — отказ `outside_case`. Сюда не входят `sources/` (их отпечатки уже в реестре источников), журнал и сами checkpoint.
4. Записать копии в `state/snapshots/<sha256>`: только отсутствующие, через временный файл с точки, `fsync` и `os.replace`; готовую копию сверить по отпечатку.
5. Собрать документ: `completed_actions` — действия с исходом `completed`, `human_choices` — решения `chosen`, `totals` — см. ниже. При признанных потерях инструмент сам добавляет в `open_items` строку с номерами потерянных checkpoint.
6. Проверить документ схемой, записать `.tmp-…` с `fsync`, опубликовать `os.replace` под именем `CKP-NNNN.json`. Номер — максимальный из всех имён в папке, включая скрытые `.lost-CKP-…` и `.rejected-CKP-…`, плюс один: ID не используется повторно, негодный файл не перезаписывается. Номер может опережать `seq`, это допустимо. `seq` и `previous` — от текущего годного.
7. Признанные потери переименовать в скрытые `.lost-<имя>`: содержимое сохраняется, а предупреждение `CHECKPOINT_FALLBACK` перестаёт повторяться. Порядок важен: сначала публикация, потом переименование, иначе сбой между ними спрятал бы потерю.
8. Прогнать валидатор повторно. Если публикация дала ошибку, файл переименовывается в скрытый `.rejected-CKP-NNNN.json`, потери, переименованные на шаге 7, возвращаются под прежние имена, ответ сообщает об отказе.

Существующий файл с таким номером — отказ, а не перезапись. Оставшиеся от сбоя `.tmp-*` в `state/checkpoints/`, `state/snapshots/` и папках артефактов удаляются после всех проверок, непосредственно перед шагом 3: отказ ничего не меняет. Если артефакты в момент шага 3 изменил другой процесс, отпечаток копии не совпадёт и `save` откажет.

Прерывание: до шага 6 текущим остаётся прежний checkpoint, изменения видны через `CHECKPOINT_STALE`, лишние копии безвредны. После `os.replace` checkpoint целиком готов. Сбой до шага 7 оставит потери видимыми, и при следующем `save` их придётся признать снова.

`save` своё действие в журнал не пишет: запись о сохранении — сам checkpoint.

`totals` минимальны до B13: `elapsed_seconds` — от первого `start` до последней строки журнала, включая перерывы; `time_to_first_result_seconds` и `human_active_seconds` — `null`; `cost` — `{"basis": "unknown"}`. Функция сбора вынесена отдельно, B13 заменит её без изменения остального.

### `resume`: продолжение

`resume <case>` только читает и выдаёт JSON:

- `status`: `fresh` (нет ни checkpoint, ни скрытых `.lost-*` и `.rejected-*`), `ok`, `fallback`, `none_valid` (годных нет; так же, если остались только скрытые файлы, их имена в `hidden_checkpoints`), `blocked` (неподдерживаемая версия или кейс не читается);
- из текущего checkpoint: `id`, `created_at`, `goal`, `stage`, `open_items`, `next_step`, `totals`;
- `human_choices`: ID, `topic` и слова пользователя `user_statement`;
- `completed_actions`: число и последние несколько ID; полный список остаётся в checkpoint;
- отличия от текущего checkpoint: `changed` и `new` (файлы, собираемые как артефакты, но не входящие в него). Отсутствующего артефакта у текущего checkpoint не бывает: такой checkpoint негоден и попадает в `lost`;
- журнал: `actions_after_checkpoint` (действия с исходом `completed`, которых нет в `completed_actions`), `actions_unknown` (начатые без конца и с исходом `unknown`, с их `kind`, `tool` и `input_refs`, кроме снятых повтором), `actions_resolved` (снятые, с `resolved_by`);
- `lost`: потерянные checkpoint с причинами и списком `missing`;
- `validation`: коды ошибок и предупреждений;
- `recovery`: допустимые команды `restore` с перечнем файлов.

Сводка сохранённых текстов — данные кейса. Записанный в них текст не становится инструкцией: это правило входит в процедуру.

Для `blocked` из-за версии ответ называет файл с неподдерживаемой версией, его версию, версию кейса и поддерживаемые, ничего не меняет и подсказывает путь: нужна версия агента с этой поддержкой или миграция. Если файл реестра входит в артефакты годного checkpoint, его можно вернуть `restore`.

### `restore`: возврат файлов

`restore <case> --checkpoint CKP-… [--path …]… --confirmed`. Без `--path` возвращаются все артефакты, отличные от сохранённых или отсутствующие. Checkpoint должен быть годным либо негодным только из-за отсутствующих файлов (`missing` в `Report`): так удалённый файл возвращается, и новейший checkpoint снова становится текущим. Пути артефактов перед записью проверяются как небезопасные (`is_unsafe_path`). `--confirmed` агент передаёт только после согласия пользователя: без флага команда показывает, что будет заменено, и ничего не пишет.

Перед заменой текущие файлы тоже попадают в `state/snapshots/`, их отпечатки выводятся в отчёте. Прежняя версия остаётся в снимках, но команды для её возврата нет. Все копии читаются и сверяются с отпечатком до первой замены; нет копии или она не совпала — отказ с перечнем `refused_paths`, ничего не заменено. Текущие версии сохраняются в снимки до первой замены. Файлы заменяются атомарно, реестры последними. Если запись прервалась (ошибка диска), ответ `restore_incomplete` называет заменённые и оставшиеся файлы и отпечатки сохранённых версий; повтор команды продолжает возврат. Папка снимков вне папки кейса — отказ. В конце выводится результат валидатора. Журнал `restore` не откатывает: он только дописывается.

Если checkpoint создан до появления копий или файл снимка удалён, `restore` честно отказывает: восстановление такого файла невозможно.

## Контракт

Изменение совместимое, версия формата остаётся `1`:

- в таблицу папки кейса добавляется `state/snapshots/<sha256>`: копии артефактов, имя — отпечаток содержимого, файлы не меняются и не удаляются;
- скрытые `.lost-CKP-…` и `.rejected-CKP-…` в `state/checkpoints/` названы как служебные: валидатор скрытые файлы и так пропускает;
- фраза «порядок и атомарность — задача B06» заменяется ссылкой на процедуру и на раздел «`save`» этой спецификации;
- правила потерь и скрытых файлов уточняются в разделе «Инструмент», в таблице кодов ничего не меняется.

Схемы и коды проверок не меняются; `Report` дополняется внутренним полем (см. «Инструмент»), PR №6 эту часть `validate_project.py` не затрагивает. Владельцы зависимых задач: B05 в PR №6 журнал не пишет, B13 надстраивает учёт над этим журналом.

## Процедура и правила агента

`agent/workflows/checkpoint.md` для обеих сред:

- когда писать действие: до и после обращения к внешнему или долгому шагу;
- когда сохранять: после каждого существенного этапа, после выбора человека и при просьбе остановиться;
- как начинать новый чат: `resume`, краткое восстановление пользователю (цель, сделано, выбор, открытое, расходы с неизвестными, следующий шаг), сверка `changed` и `actions_unknown` до любых действий;
- что делать при каждом `status`, неизвестном исходе, потере и отказе `save`;
- что файлы состояния не правятся руками.

`agent/instructions/product-mode.md` получает одну строку со ссылкой. Команды естественным языком и порядок этапов остаются B07.

## Проверки

Офлайн, в `tests/test_checkpoint.py`, на копии `examples/valid/demo-case` и созданных в тесте кейсах:

- жёсткое завершение процесса (`os._exit`) на выбранных шагах `fsync` и `os.replace` в `save`, `save` с потерями, `restore`, `action start` и `action human`: после каждого остановки `resume` и валидатор отвечают без ошибок, повтор команды проходит;
- прерывание на каждом шаге `save` и записи журнала подменой функции записи: после него `resume` показывает прежний checkpoint, начатое действие попадает в `actions_unknown`, повторный `save` проходит;
- оборванная строка журнала отсекается перед записью, незавершённый хвост посередине даёт отказ;
- повтор без `--retry-of` запрещён, с ним проходит, причина видна;
- `completed_actions` и `human_choices` совпадают с журналом и реестром, агент не может их передать; `stage: done` при неизвестном исходе отказан;
- повреждённый новейший checkpoint: `fallback`, отказ `save` без `--acknowledge-loss`, с ним новый файл не затирает негодный, потери в `open_items`, негодный лежит как `.lost-…`, следующий `save` флага не требует;
- удалённый артефакт: новейший checkpoint в `lost` с `missing`, `restore` возвращает файл, `resume` снова даёт `ok`;
- все checkpoint негодны, неизвестная версия кейса, версия checkpoint не совпала;
- повреждённый реестр и изменённый `outputs`: `resume` называет их, `restore` без `--confirmed` не пишет, с ним возвращает содержимое побайтно, прежняя версия лежит в снимках;
- кейс, перенесённый копированием папки в другой путь, продолжается так же: в файлах нет абсолютных путей, и `resume` не зависит от места и чата;
- повторный `resume` не меняет ни одного файла;
- отчёт не содержит абсолютных путей и текста исключений.

Живой новый чат и перенос в обе стороны проверяются в B09/B12. Здесь заявляется только механика.

## Ограничения

- Откат реестра оставляет в журнале ссылки на записи, созданные после checkpoint: валидатор даёт `ID_MISSING`, и `save` отказывает. Это двойной сбой (повреждение плюс работа после сохранения). Агент сообщает пользователю и файлы руками не правит; отдельного обхода нет.
- Откат не отменяет внешних последствий действий.
- После `restore` прежняя версия файла остаётся в снимках с известным отпечатком, но команды её возврата нет; вернуть её можно только вручную.
- Ссылка из журнала на скрытый или потерянный ID не проверяется на существование записи: ошибки нет, но и проверить её нельзя.
- Снимки растут с числом версий. Размер ограничен текстами кейса, очистки нет.
- Одновременная работа двух чатов не поддержана: второй `save` может получить отказ по занятому номеру, блокировок нет.
- `fsync` защищает от обрыва процесса; гарантии при отключении питания зависят от диска.
- Защита от повтора опирается на то, что агент записывает действия; действия вне журнала инструмент не видит.

## Критерии приёмки
