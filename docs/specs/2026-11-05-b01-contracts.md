# B01. Контракты данных и режимы

Спецификация задачи B01 из [карточек](../tasks/CORE.md), уточняет раздел 5 [ТЗ](2026-11-04-product-agent-tz.md). Статус: согласована командой 5 ноября 2026 года.

## Зачем

После B01 параллельно начинаются B04, B06, B07 и B13. Им нужны общие ID, форматы и правила, иначе каждая задача придумает свои, и они разойдутся уже в B09. Отдельно нужно развести два способа работы с одной папкой: руководитель продукта ведёт кейс и не должен сталкиваться с ветками и PR, а участник команды меняет репозиторий по правилам разработки.

Успех: другой исполнитель по документам B01 пишет запись любой сущности без чтения этой спецификации, а валидатор находит нарушения связей до того, как они попадут в стратегию.

## Цели и границы

Входит:

1. Схемы JSON всех сущностей раздела 5 ТЗ, документация путей, ID и версий.
2. Минимальный валидный пример кейса и набор невалидных примеров.
3. Валидатор папки кейса: схема и связи.
4. Маршрутизатор режимов в корневых `AGENTS.md` и `CLAUDE.md`, перенос правил разработки в отдельный файл, минимальный файл режима продукта.

Не входит: запись и обновление реестров (B05), запись checkpoint и восстановление (B06), сводка учёта (B13), `START.md` и этапы (B07), извлечение текста (B04), расчёты (B10), графовая БД, семантический поиск.

Провал даже при зелёных тестах: контракт требует от пользователя править JSON руками, зависит от чата или `.work/`, содержит личные пути, либо модель может записать свой выбор как выбор человека без видимого следа.

## Файлы

```text
agent/contracts/

  modes.md                  — правила режимов

  schemas/*.schema.json     — по одной схеме на тип файла

  examples/invalid/<случай>/ — один нарушенный случай на папку

tools/validate_project.py

```

В `.gitignore` добавляется `projects/`: пользовательские кейсы по умолчанию не публикуются. Примеры лежат в `agent/contracts/examples/`, а демонстрационные материалы позже — в `examples/`.

## Папка кейса

Пути заданы от корня `projects/<case-id>/`:

| Файл | Содержимое | Запись |
|---|---|---|
| `case.json` | Версия формата, ID кейса, название, дата создания | Один раз |
| `brief.md` | Бриф | Текст, без контракта |
| `sources/` | Копии материалов пользователя и скачанных файлов; извлечённый текст — `sources/extracted/<SRC-id>.*`, формат определяет B04 | Файлы, не меняются после регистрации |
| `evidence/sources.json` | Источники | Реестр |
| `evidence/claims.json` | Утверждения | Реестр |
| `evidence/calculations.json` | Расчёты | Реестр |
| `research/questions.json` | Вопросы исследования | Реестр |
| `decisions/options.json` | Варианты | Реестр |
| `decisions/decisions.json` | Предложения и выбор | Реестр |
| `outputs/*.md` | Стратегии и план проверки | Текст, ссылки `[CLM-0001]` |
| `state/actions.jsonl` | Журнал действий | Только дописывание |
| `state/checkpoints/CKP-*.json` | Checkpoint | Новый файл на сохранение |

Реестр — JSON вида `{"format_version": 1, "records": [...]}`. Запись не удаляется: отзыв выражается статусом и причиной. Кейс без файла реестра считается кейсом с пустым реестром, обязателен только `case.json`.

## ID и версии

- Формат `ПРЕФИКС-NNNN`: `SRC`, `CLM`, `CALC`, `Q`, `OPT`, `DEC`, `ACT`, `CKP`. Минимум четыре цифры.
- ID уникален внутри кейса и не используется повторно, включая отозванные записи. Префикс задаёт тип, поэтому ссылка на запись другого типа — ошибка.
- `case_id`: строчные латинские буквы, цифры, дефис; совпадает с именем папки.
- Даты — RFC 3339 со смещением.
- Пути — относительные от корня кейса, через `/`, без `..` и букв диска. Абсолютный путь — ошибка: он не переносится и раскрывает личные данные.
- `format_version` — целое число. Первая версия — `1`. Поддерживаемые перечислены в `versions.json` вместе со ссылкой на миграцию.

`format_version` есть в `case.json`, реестрах, checkpoint и каждой строке журнала; у Markdown версии нет. Несовместимое изменение увеличивает версию. Для неизвестной версии в `case.json`, реестре или журнале валидатор останавливается с кодом `FORMAT_UNSUPPORTED` и не читает записи. Известная версия, отличная от `case.json`, — `FORMAT_MIXED`. Отсутствие поля — `SCHEMA`. Checkpoint с другой версией не останавливает проверку: он негоден, чтобы восстановление могло опереться на более ранний.

Миграция: скрипт `tools/migrate_v<N>.py`, добавляется вместе с новой версией. Он создаёт рядом копию кейса в новом формате, исходная папка не меняется, результат проходит валидатор. В B01 скрипта нет, так как есть только версия 1; порядок описан в `agent/contracts/README.md`. Изменение контракта согласуется с владельцами зависимых задач в PR.

## Сущности

Состав полей раздела 5 ТЗ сохранён. Ниже только то, что ТЗ не определяет. Все названные поля обязательны, если не сказано иное. У всех записей есть `id` и `created_at`. Неизвестное значение — `null`, а не ноль и не пустая строка.

Отзыв единообразен. У `SRC`, `CALC`, `Q`, `OPT` есть `record_status`: `active` или `withdrawn`, при `withdrawn` обязателен `status_reason`. У `CLM` эту роль играет `status: withdrawn` с тем же `status_reason`, у `DEC` — `status: superseded`. `ACT` и `CKP` не отзываются.

**Источник (`SRC`).** `type`: `md`, `txt`, `docx`, `pdf`, `csv`, `xlsx`, `web`. `location`: ровно одно из `path` или `url`; `path` начинается с `sources/`, `url` — только `http` или `https`. Необязательное `source_url` хранит адрес скачанного файла. `origin`: `user_provided`, `public_web`, `own_training`. `allowed`: логическое, `false` запрещает использовать источник как подтверждение. `retrieved_at`. `sha256`: отпечаток файла, для `url` — `null`. `extraction`: `status` из отчёта чтения B02 плюс `unavailable` для сайта: `ok`, `partial`, `empty`, `unreadable`, `unsupported`, `over_limit`, `unavailable`; `complete`, логическое; `limits`, текст границ.

**Локатор.** Объект с `kind`:

| `kind` | Поля | Для типов |
|---|---|---|
| `section` | `heading` | `md`, `txt`, `docx`, `web` |
| `paragraph` | `index` | `docx`, `md`, `txt`, `web` |
| `page` | `page` | `pdf` |
| `cells` | `sheet`, `range` | `xlsx` |
| `rows` | `from`, `to` | `csv` |
| `doc_table` | `table`, `row` | `docx`, `web` |

Индексы начинаются с единицы и считаются по извлечённому тексту: абзац отделён пустой строкой, в DOCX абзац — элемент документа. Необязательное поле `quote` хранит короткую цитату, подтверждающую утверждение. У страницы сайта адрес уже есть в источнике.

**Утверждение (`CLM`).** `kind`: `fact`, `hypothesis`, `forecast`, `inference`. Значение `inference` — наше дополнение к ТЗ для вывода модели из других записей: ТЗ требует, чтобы прежний ответ модели оставался выводом, а не фактом. `status`: `confirmed`, `unconfirmed`, `contested`, `withdrawn`. `supports` и `contradicts` — списки `{source_id, locator, note}`. У `contradicts` необязательное `resolution` — объяснение, почему противоречие снято. `derived_from`: ID утверждений и расчётов. `limits`: текст ограничений. Процент уверенности отсутствует.

**Расчёт (`CALC`).** `inputs`: `{name, source_id, locator, value, unit, period}`; вместо `source_id` и `locator` вход может указывать `calculation_id` другого расчёта. `method`: `{kind: "tool" | "formula", description}`. `result`: `{status: "computed" | "not_computable", value, unit, period}`. `gaps`, `assumptions`, `reproduce`: команда от корня репозитория без личных путей либо формула. Детали операций определяет B10.

**Вопрос (`Q`).** `question`, `affects`, `needed_evidence`, `status`: `open`, `answered`, `partial`, `blocked`; `findings`: ID утверждений и расчётов; `gap`.

**Вариант (`OPT`).** Поля раздела 3.4 ТЗ. `strategy_kind`: `keep`, `close`, `develop`. `basis`: ID утверждений и расчётов. `objections`: непустой список текста.

**Решение (`DEC`).** Запись разделяет предложение и выбор:

```json
{
  "id": "DEC-0002",
  "topic": "direction",
  "status": "chosen",
  "proposal": {"option_id": "OPT-0003", "rationale": "...", "proposed_at": "...", "action_id": "ACT-0020"},
  "choice": {"option_id": "OPT-0001", "user_statement": "Закрываем направление", "chosen_at": "...", "action_id": "ACT-0021"},
  "supersedes": "DEC-0001",
  "change_reason": "Пользователь изменил ограничение по бюджету"
}
```

`topic` — короткий идентификатор предмета решения, в обязательном сценарии `direction`. На один `topic` приходится одна цепочка замен, в ней одна незаменённая запись. Запись `proposed` становится `chosen` на месте: добавляется `choice`. Новая запись с `supersedes` нужна, когда меняется предложение или уже сделанный выбор, прежняя получает `superseded`.

`proposal` равно `null`, если пользователь сам назвал направление без предложения агента: такая запись сразу `chosen`. `status`: `proposed`, `chosen`, `superseded`. Поля «кто выбрал» нет: `choice` по определению принадлежит человеку и обязан ссылаться на действие типа `human_input`, а `proposal.action_id` — на действие типа `model`. Это не доказывает слова пользователя, но делает подлог видимым в журнале. Выбор может отличаться от предложения.

**Действие (`ACT`).** Строка JSONL на событие, у одного действия две строки:

```json
{"format_version": 1, "id": "ACT-0007", "phase": "start", "kind": "web_read", "tool": "WebFetch", "environment": "claude_code", "model": "...", "input_refs": ["SRC-0002"], "at": "..."}
{"format_version": 1, "id": "ACT-0007", "phase": "end", "outcome": "completed", "result_refs": ["SRC-0002"], "cost": {"basis": "unknown"}, "at": "..."}
```

`kind`: `model`, `search`, `web_read`, `file_read`, `compute`, `save`, `human_input`. `environment`: `claude_code`, `codex`. `outcome`: `completed`, `failed`, `unknown`. Начало без конца означает неизвестный исход: перед повтором его нужно проверить. Каждая строка заканчивается переводом строки. Перед дописыванием писатель отсекает незавершённую последнюю строку: удаляет её, иначе она склеится со следующей записью. Необязательные `retry_of` и обязательный при нём `retry_reason` ставятся на строке `start`. `cost.basis`: `measured`, `estimated`, `unknown`. При `unknown` полей суммы нет, поэтому неизвестное не превращается в ноль. При `measured` и `estimated` суммы лежат в `amounts`: `input_tokens`, `output_tokens`, `money_usd`, каждое необязательно. При `estimated` значение может быть диапазоном `{min, max}`. При `estimated` обязателен `estimate_source`. Точный состав учёта уточняет B13 без изменения этих полей.

`human_input` записывает агент, когда ответ уже получен: обе строки сразу, поэтому ожидание ответа действием не считается. `input_refs` пуст, `result_refs` содержит ID записи, созданной по ответу, например решения. Слова пользователя лежат в `user_statement` решения, а не в журнале.

**Checkpoint (`CKP`).** Поля: `format_version`, `id`, `case_id`, `created_at`, `seq`, `previous` (ID либо `null`), `goal`, `stage`, `artifacts`, `completed_actions`, `human_choices`, `open_items`, `next_step`, `totals`. `stage`: `intake`, `research`, `options`, `decision`, `strategies`, `validation_plan`, `done`. `artifacts`: `{path, sha256}`, отпечаток служит версией. `completed_actions`: ID. `human_choices`: ID решений. `open_items`: текст. `totals`: `elapsed_seconds`, `time_to_first_result_seconds`, `human_active_seconds` (число либо `null`) и `cost` с тем же правилом неизвестного.

Негодный checkpoint — неразбираемый, с нарушением схемы или версии, чужим `case_id`, отсутствующим артефактом, расхождением `id` с именем файла либо нарушением цепочки: `seq` растёт на единицу от `previous`. Для негодного файла номер берётся из имени, поэтому потеря новейшего всегда видна. Текущий — годный с наибольшим `seq`. Отдельного указателя нет: он потребовал бы второй записи, и сбой между ними дал бы ложное состояние. Порядок записи и атомарность реализует B06.

Несовпадение отпечатка не делает checkpoint негодным: так выглядит и правка стратегии до следующего сохранения, и прерванная запись новых артефактов, а более ранний checkpoint от этого не лучше. Валидатор выдаёт предупреждение `CHECKPOINT_STALE` со списком файлов, агент сверяет их перед продолжением и сохраняет новый checkpoint.

## Правила связей

Схема проверяет форму, правила ниже — смысл. Проверяются только активные записи: `withdrawn` и `superseded` остаются в истории и не блокируют кейс.

Ошибки:

| Код | Условие |
|---|---|
| `ID_DUPLICATE` | ID повторён в кейсе |
| `ID_MISSING` | Ссылка на несуществующий ID |
| `ID_WRONG_TYPE` | Ссылка на запись другого типа |
| `CLAIM_NO_BASIS` | `confirmed` без `supports`; `inference` без `derived_from` при любом статусе |
| `SOURCE_MISSING` | Файл активного источника отсутствует |
| `SOURCE_CHANGED` | Отпечаток файла активного источника другой: основания больше не проверены, нужна новая запись источника |
| `CLAIM_WEAK_SOURCE` | Основание `confirmed` — отозванный, запрещённый или нечитаемый источник (`empty`, `unreadable`, `unsupported`, `over_limit`, `unavailable`) |
| `CLAIM_WEAK_DERIVATION` | `confirmed` опирается на запись не в статусе `confirmed`, на нерассчитанный расчёт, на расчёт от слабого источника либо на самого себя через цепочку `derived_from` |
| `CLAIM_CONFLICT_HIDDEN` | `confirmed` при `contradicts` без `resolution` |
| `CLAIM_NOT_CONTESTED` | `contested` без `contradicts` |
| `FACT_NOT_CONFIRMABLE` | `confirmed` при `kind` не `fact` и не `inference` |
| `STATUS_NO_REASON` | `withdrawn` без `status_reason` |
| `LOCATOR_MISMATCH` | Вид локатора не подходит типу источника |
| `LOCATOR_NOT_FOUND` | У источника есть извлечённый текст, но локатор не указывает ни на один его блок |
| `QUOTE_NOT_FOUND` | Цитата локатора не входит в текст блоков, на которые он указывает |
| `WITHDRAWN_USED` | Активный вариант, решение, вопрос, расчёт или текст `outputs/*.md` ссылается на отозванную запись |
| `DECISION_CHOICE_STATE` | `chosen` без `choice` либо `proposed` с `choice` |
| `DECISION_NOT_HUMAN` | `choice.action_id` не завершённое действие `human_input` с этим решением в `result_refs`; `proposal.action_id` не действие `model` |
| `DECISION_SUPERSEDE` | `supersedes` без `change_reason`; заменённое решение не в статусе `superseded`; у `superseded` нет заменяющего; цикл, ветвление или смена `topic` в цепочке |
| `DECISION_MULTIPLE_ACTIVE` | Больше одной незаменённой записи на `topic`, считая `proposed` |
| `ACTION_RETRY` | `retry_of` без `retry_reason`, `retry_reason` без `retry_of` либо повтор самого себя |
| `ACTION_ORDER` | `end` без `start` либо два `end` |
| `ACTION_COST` | Сумма при `unknown` либо `estimated` без `estimate_source`; денежная оценка без даты тарифа в `estimate_source` (B13) |
| `ACTION_HUMAN` | Объект `human` не на `human_input`; выбор без решения в `result_refs`; обход поломки без `note` (B13) |
| `OUTPUT_LINK` | В `outputs/**/*.md` ссылка на несуществующую запись, на `ACT` или `CKP`, либо скобка с похожим на ID, но неверным значением. В одной скобке допустимо несколько ID через запятую |
| `CHECKPOINT_CLAIM` | Текущий checkpoint называет выбором человека решение без `choice` либо завершённым действие без исхода `completed` |
| `PATH_UNSAFE` | Абсолютный путь либо выход за корень кейса в полях путей и в `reproduce`, `url` не `http` и не `https` |
| `SCHEMA` | Нарушение схемы, включая неверную дату и значения ID с посторонними символами |
| `FORMAT_UNSUPPORTED`, `FORMAT_MIXED` | Версия формата |
| `CASE_INVALID` | Нет `case.json` либо `case_id` не совпадает с папкой |
| `FILE_CORRUPT` | Файл не разбирается как JSON |
| `TIME_IN_FUTURE` | `created_at`, `proposed_at` или `chosen_at` записи реестра позже текущего времени больше чем на пять минут |
| `CALC_MISMATCH` | Активный расчёт с `method.formula` не следует из своих входов: значение входа расходится с материалом или результатом входящего расчёта, либо результат — с формулой (B10). Не выдаётся, если у записи уже есть ошибка ссылки, локатора, цитаты или отзыва |
| `SYNTHETIC_NOT_EVIDENCE` | Синтетический источник (`origin: synthetic`), в том числе отозванный, среди `supports` активного утверждения, которое не `hypothesis` или `confirmed`, среди `contradicts` активного утверждения или среди входов активного расчёта (E03). Отозванные и замещённые утверждения и расчёты, как и для прочих связей, не проверяются |
| `SYNTHETIC_PATH` | `origin: synthetic` у источника вне `sources/interviews/synthetic-*` либо такой путь с другим `origin` (E03) |

Предупреждения, не меняющие код выхода:

| Код | Условие |
|---|---|
| `BASIS_UNCONFIRMED` | Вариант, решение или текст `outputs/**/*.md` опирается на `unconfirmed` либо `contested`, либо у варианта пустой `basis`: допустимо, но должно быть видно |
| `SOURCE_PARTIAL` | Подтверждение идёт из частично прочитанного источника |
| `EXTRACT_MISSING` | У источника со статусом чтения `ok` или `partial` нет файла извлечённого текста: локаторы проверить нечем |
| `CALC_UNVERIFIED` | Рассчитанный (`computed`) активный расчёт без `method.formula`: число записано вручную и не пересчитывается; либо у входа расчёта с формулой нет извлечённого текста, и формула проверена только по записанным значениям входов (B10) |
| `REGION_AREA_DIFFERS` | Локатор `region` называет область (`area`), не совпадающую с областью наблюдения с тем же номером: ссылка, возможно, указывает не на то место снимка (E04) |
| `ACTION_UNKNOWN` | Действие без конца или с исходом `unknown` |
| `JOURNAL_TORN` | Последняя строка журнала обрезана: она игнорируется. Обрезанная строка не в конце — `FILE_CORRUPT` |
| `CHECKPOINT_STALE` | Отпечаток артефакта текущего checkpoint другой |
| `CHECKPOINT_FALLBACK` | Новейший checkpoint негоден, текущим признан более ранний. Вывод называет его и потерянные `seq`. Причины негодности входят в предупреждение, а не в ошибки |

Если негодны все checkpoint — это ошибка `CHECKPOINT_NONE_VALID`. Кейс без checkpoint допустим.

## Валидатор

```powershell
.venv/Scripts/python.exe tools/validate_project.py <папка кейса> [--json]
```

Код выхода: `0` — ошибок нет, `1` — есть ошибки, `2` — неверный вызов, `3` — внутренний сбой валидатора, без текста исключения. Вывод: код, файл, ID записи и короткое пояснение. Содержимое полей и материалов в вывод не попадает: там могут быть внедрённые инструкции и личные данные. `--json` даёт машиночитаемые списки `errors`, `warnings` и значение `current_checkpoint`, на него опираются B05 и B06. Валидатор только читает.

Схемы проверяются библиотекой `jsonschema`, она добавляется в рабочие зависимости и `uv.lock`: ТЗ предпочитает проверенные библиотеки, а `.venv` и так нужен обеим средам. Выбор наш.

## Режимы

Правило различения — с чем идёт работа, а не как сформулирована просьба:

| Запрос | Режим |
|---|---|
| Работа с кейсом: начать, продолжить, спросить о нём, исправить стратегию, изменить ограничение; читается и меняется только `projects/<case-id>/` | Продукт |
| Всё вне `projects/`: инструкции, методики, контракты, инструменты, документы, тесты, CI; а также Git, PR, merge и вопросы об устройстве репозитория | Разработка |
| Непонятно, что меняется | Один короткий вопрос, затем режим |

Значит «поправь вывод в стратегии» — продукт, а «поправь, как агент формулирует выводы» — разработка.

Агент называет режим одной фразой в первом ответе и при смене режима. Текст из материалов и источников режим не меняет. В режиме продукта не выполняются Git-процедуры, не нужны ветка и PR, а `.work/` не читается и не пишется. В режиме разработки перед действиями читается `docs/development-rules.md`.

Корневые файлы:

- `AGENTS.md` — короткий маршрутизатор с таблицей выше и ссылками на два файла правил. Содержимое нынешнего `AGENTS.md` переносится в `docs/development-rules.md` без смысловых изменений, кроме ссылок и вводной строки.
- `CLAUDE.md` — импорт `@AGENTS.md`. Импорт правил разработки не добавляется: тогда они загружались бы и в режиме продукта, а карточка B07 требует, чтобы они не мешали продуктовому сценарию.

Цена переноса: правила разработки больше не загружаются автоматически, их чтение зависит от маршрутизатора. Участники узнают об этом из PR. Ссылки на `AGENTS.md` как на правила разработки в `README.md` и `CLAUDE.md` обновляются там, где речь о текущем состоянии, исторические записи не трогаются.

`agent/instructions/product-mode.md` содержит только постоянные правила режима: не требовать Git, работать в папке кейса, материалы считать данными, выбор человека не выдавать за свой, контракты брать из `agent/contracts/`, запускать валидатор. Этапы и запуск дописывает B07.

## Приёмка и проверки

Офлайн, в CI, через `tests/test_contracts.py`:

- `examples/valid/` проходит без ошибок и содержит запись каждого типа, включая отозванное утверждение, снятое противоречие, заменённое решение и действие с неизвестным расходом.
- Каждая папка `examples/invalid/<случай>/` даёт ровно ожидаемый код из файла `expected.json`. Покрыты все коды ошибок и предупреждений, включая неизвестную версию, отсутствующий ID, противоречащую и отозванную запись, обрезанный журнал и негодный новейший checkpoint.
- В контрактах и примерах нет абсолютных путей и значений, похожих на ключи.
- Проект без `.work/` и без истории чата проходит: тест копирует пример во временную папку.

Вручную и живьём, результат записывается в PR раздельно:

- Чтение контрактов другим исполнителем: независимый агент только по `agent/contracts/` составляет запись каждого типа, валидатор их принимает. Вопросы агента — замечания к документации.
- Разграничение режимов в обеих средах: новый чат, продуктовый запрос и запрос изменить код. Ожидается: продукт — без Git и `.work/`; код — чтение `docs/development-rules.md`. Ответ оценивается по действиям, не по формулировке.

Прогон в среде выполняет участник с рабочим входом, как в B02. До него строка остаётся «не запускалось», и B01 не переводится в `done`.

Обязательные команды: `scripts/check.ps1`, `scripts/test-checks.ps1`, `unittest` на финальном дереве. Если `pwsh` локально нет, они запускаются из временной копии вне репозитория; системная установка не меняется.

## Что решает исполнитель

Точные имена необязательных полей внутри разделов ТЗ, тексты сообщений валидатора, разбиение схем на общие `$defs`, состав данных примера. Примеры используют явно вымышленные учебные данные.

## Наши решения, требующие внимания при согласовании

1. Новый тип утверждения `inference`, которого нет в перечне ТЗ.
2. `format_version` как целое число, без минорных версий.
3. Журнал из двух событий на действие: это даёт неизвестный исход без отдельной записи.
4. Отсутствие указателя на текущий checkpoint. Изменённый артефакт даёт предупреждение, а не негодный checkpoint.
5. Правила разработки не импортируются в `CLAUDE.md`.
6. Новая зависимость `jsonschema`.
7. Изменённый файл источника — ошибка: правка материала задним числом не должна оставлять старые подтверждения в силе.
