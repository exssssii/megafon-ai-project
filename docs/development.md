# Подготовка клона и проверки

Нужны Git, PowerShell 7 (`pwsh`), `uv` и Python 3.12. PowerShell 7 ставить необязательно: хватит распакованного архива, тогда вместо `pwsh` вызывается полный путь к `pwsh.exe`. Проверки репозитория не устанавливают пакеты, не вызывают модели и не используют платные API. Продуктовые зависимости, маршруты сред и пределы входов описаны в [заметке B02](environments.md).

## Подготовить свой клон

Из корня репозитория выполнить:

```powershell
pwsh -NoProfile -File scripts/setup-hooks.ps1
```

Команда включает `.githooks` только для текущего клона и исключает `.work/` через локальный `.git/info/exclude`. Глобальная конфигурация не меняется. При уже установленном другом наборе hooks нужно разрешить конфликт, а не отключать существующую защиту.

В каждом клоне участник использует собственный подтверждённый аккаунт и локальную Git-личность. Общей учётной записи команды нет. Авторизация и автор коммита проверяются отдельно; секреты не передаются между участниками.

## Проверить изменения перед коммитом и PR

```powershell
pwsh -NoProfile -File scripts/check.ps1
pwsh -NoProfile -File scripts/test-checks.ps1
```

[Проверка репозитория](../scripts/check.ps1) проверяет Markdown, локальные ссылки, определения требований, карточки задач, зависимости и покрытие. Внешние ссылки не скачиваются. Число задач и требований определяется из документов; новый корректный пункт не требует править магическое число в проверке.

[Проверочные сценарии](../scripts/test-checks.ps1) проверяют, что реальные дефекты обнаруживаются: несуществующий путь, неверная зависимость, цикл и непокрытое требование. Защита `main` проверяется на временных локальных Git-репозиториях. Тесты не выполняют push в рабочую `main` и не используют сеть.

Хук `tools/web_guard.py` отклоняет поиск и чтение страниц без записи в журнал незавершённого кейса, с которым работали за последние 12 часов. Для работы над репозиторием рядом с таким кейсом выставить `CASE_WEB_GUARD=off`.

Хук `tools/respondent_guard.py` подключён только в определении субагента `.claude/agents/respondent.md` и действует, пока тот работает: модельному собеседнику разрешено читать один файл `agent/roles/respondent.md`. При ошибке или без `.venv` хук отказывает, а не пропускает.

Хук `tools/reviewer_guard.py` так же подключён только в `.claude/agents/reviewer.md`: проверяющему разрешены `Read`, `Glob` и `Grep` внутри папок кейсов в `projects/`, кроме их `state/` и чтения сводки учёта `accounting.md`, и чтение `agent/roles/reviewer.md`. `Glob` и `Grep` без пути отклоняются.

Офлайн-тесты локальных инструментов:

```powershell
uv sync --locked
.venv/Scripts/python.exe -m unittest discover -s tests
```

В [CI](../.github/workflows/ci.yml) запускаются те же команды, тесты инструментов — через `uv run --locked`. CI идёт на GitHub-hosted раннерах `ubuntu-latest` и `windows-latest`. Проверки выполняются при изменении PR в `main` и после изменения самой `main`; отдельный push рабочей ветки не создаёт второй одинаковый прогон открытого PR. На Windows CI также выполняет сухой прогон наборов `entry`, `strategy`, `e2e`, `hard` и `interviews` скрипта `scripts/live-entry.ps1` в обеих средах: без модели, но с подготовкой клона, кейсов и архивов, чтобы поломка подготовки была видна при слиянии, а не накануне живого прогона. Кейс `family-connect` набора `hard` проходит сухой прогон на сгенерированном файле вместо PDF брифа (`-Brief`): проверяется, что бриф попадает в `inbox/` клона и не попадает в архивы. Набор `hard` дополнительно проходит сухой прогон с ключом `-PlainChat`: это обычный чат сравнения E06, клон без инструкций, методик, утилит и навыков продукта. Он же проходит сухой прогон с ключом `-NoReviewer`: вариант сравнения без независимого проверяющего E02, в клоне нет его роли и объявлений. Каждый живой прогон записывает начало и конец каждой реплики в `timing.tsv`, сводка прогона показывает секунды по репликам и их сумму. Наборы `continue`, `faults` и `finish` требуют архив прошлого прогона и в CI не запускаются. Workflow получает только права чтения содержимого. Внешние reusable actions не подключены.

Зелёный CI означает прохождение перечисленных проверок репозитория. Он не подтверждает пока отсутствующий продукт, живую модель, сценарий работы с продуктом или качество стратегий. По мере реализации B-задач в CI добавляются их реальные офлайн-проверки, а живые и визуальные прогоны учитываются отдельно.

## Защита основной ветки и авторство

Локальный `pre-push` запрещает изменения и удаление удалённой `refs/heads/main`, включая push из другой локальной ветки. После установки проверить `git config --local --get core.hooksPath`: ожидается `.githooks`. Новый клон требует собственной установки; локальный hook не является серверным ограничением. Обход через `--no-verify` и отключение hooks запрещены правилами проекта.

Слияние в `main` идёт только через squash-PR и только после зелёного CI на текущем head. Перед слиянием проверяются актуальность `main` и замечания ревью.

Проектная `.claude/settings.json` отключает автоматическую атрибуцию коммитов/PR и ссылку сессии; остальные настройки не меняются. Значения описаны в [официальной документации Claude Code](https://code.claude.com/docs/en/settings-reference#attribution). Перед публикацией всё равно читать сообщения коммитов и окончательное описание PR.
