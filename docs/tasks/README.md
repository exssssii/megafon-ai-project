Статус: ТЗ и карточки согласованы с обязательной поддержкой Claude Code и Codex. Выбран порядок «обязательное ядро, затем отдельные улучшения». Продуктовая реализация начата с контрактов B01. Пустая начальная main создана разовым решением команды; B00 принята: PR №1 с проверками и инструкциями разработки слит.

Основные документы: [ТЗ](../specs/2026-11-04-product-agent-tz.md), [19 обязательных карточек B00–B18](CORE.md), [кандидаты улучшений](IMPROVEMENTS.md), [мелкие доработки](POLISH.md). Прежний E05 включён в обязательную поддержку двух сред, остальные ID сохранены. Это общая постановка команды; локальные планы исполнителей не заменяют её.

## Как выбираем следующую задачу

1. Задача имеет понятные границы, входы, результат и критерии приёмки; существенные решения согласованы.
2. Все её обязательные зависимости приняты по критериям соответствующих карточек. «Есть код» или «открыт PR» не равно завершённой зависимости.
3. Задача свободна: проверены текущий код и PR; владелец закреплён однозначно по правилам разработки. Для подготовительного анализа без реализации достаточно явно указанного исполнителя.
4. Из доступных задач сначала выбираем ту, которая открывает критический путь либо снимает самый существенный риск; затем учитываем приоритет и срок. Не назначаем искусственную последовательность независимым задачам.
5. Учитываем изменения в общих файлах и контрактах. Независимость по функции не гарантирует отсутствия конфликта редактирования.

Приоритет и зависимость — разные вещи: задача с высоким приоритетом может ждать входов; свободный участник в это время берёт другую готовую задачу. При блокировке записать недостающий вход и точное условие разблокировки.

Статусы: `todo` — не выполнены зависимости или ещё не проработана карточка; `ready` — можно брать; `in_progress` — закреплена и выполняется; `review` — ждёт приёмки; `blocked` — возник конкретный блокер; `done` — принята. В `done` сохраняются доказательства проверки. Для реализации туда входят нужные проверки и влитый PR; для решения команды — её явное согласование.

## Устройство подготовленного ТЗ

Один документ в `docs/specs/` описывает результат для пользователя и границы реализации. Общая очередь и короткие карточки в `docs/tasks/` служат навигацией для команды. Локальный план конкретного исполнителя хранится в `.work/plans/`; он не заменяет общие постановки и не содержит единственную копию зависимостей.

Порядок описания ТЗ:

1. Польза, основной пользователь и задачи, выбранное отличие, цели и осознанные отказы.
2. Соответствие требованиям кейса и обязательные материалы сдачи.
3. Полный пользовательский сценарий, точки выбора человека, остановка, исправление, новый чат.
4. Архитектура папки: инструкции, методики, источники, проектные данные, состояние и результаты.
5. Работа с документами/таблицами/сайтами, проверяемыми основаниями и расчётами.
6. Варианты, возражения, продуктовая/коммуникационная стратегии и план проверки.
7. Память и дополнительные возможности выбранной концепции, ошибки и восстановление, безопасность.
8. Основная среда, доступы, зависимости, расходы, переносимость и ограничения.
9. Протоколы приёмки, сравнение, демонстрация, чистый запуск и итоговый комплект.
10. Связь с карточками задач, этапами, критическим путём и условиями остановки новых функций.

## Формат карточки реализации

```text
ID и название:
Приоритет:
Связанные требования: Fxx / Sxx / Oxx
Цель и наблюдаемый результат:
Зависимости (ID и нужный принятый результат):
Входы и существующие контракты:
Границы работы и явные исключения:
Выходные файлы / интерфейсы / артефакты:
Критерии приёмки:
Проверки и доказательства:
Риски и условие разблокировки:
Статус:
Владелец:
Ветка / PR:
Версия и фактический результат проверки:
```

Карточка должна позволять исполнителю работать без восстановления всей истории обсуждения. Задачи делятся по проверяемому результату; инструкция «сделать память» без входов, правил обновления и проверки восстановления недостаточна.

## Порядок реализации, который предстоит детализировать

Последовательность по обязательным требованиям: согласованные форматы состояния и источников → минимальный сквозной сценарий с сохранением и новым чатом → сложные сценарии и независимый кейс → чистый запуск → окончательные документы и видео. Измерения начинаются с первого прогона. Чтение материалов, вычисления и подготовка проверки могут идти независимо после согласования используемых ими контрактов. Улучшения добавляются отдельно после приёмки ядра.

Восстановление, происхождение фактов и защита входных материалов закладываются в минимальную цепочку; их нельзя оставить на финальную доработку. Измерения и черновик демонстрации начинаются с первых прогонов, хотя итоговые отчёт и видео относятся к сдаваемой версии.
